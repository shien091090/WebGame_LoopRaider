### 提案 1 — 放進「說明頁」, 合併到「示意圖裡任何依幾何判定的狀態…用 node 驗算」那條的再現
- 說明頁的小關卡要示意「同一關兩條路線」(繞上層平台 vs 沿地面直衝), 初稿把上平台用的懸空階梯擺在離地 80px(頂面), 跳得上去; 但階梯底只離地 40px, 直衝路線的玩家(高 44)從底下走過會撞頭, 圖上卻看不出來(LoopRaider deepen-1 game-a 建置自查, 非老闆回饋, 不算升格證據; 第一個平台跳躍情境) → 只驗了「跳得上去」(跳躍高度 ≥ 階差), 沒驗「從下面過得去」(淨空 ≥ 角色高); 平台關卡的懸空地形同時被兩條規則用到 → 示意圖裡每塊懸空地形對每條畫出來的路線各驗一次: 要站上去的驗跳躍高度、要從下面穿過的驗淨空(地形底到地面 ≥ 角色判定高), 兩個條件常把位置夾在一個窄區間(該作: 頂面離地 84~108px), 驗算寫進 style.md 說明頁表〔P3〕

### 提案 2 — 放進「與規格的分界」, 新經驗
- 介面要求方向性特效(擊飛速度線「畫在飛行反方向」、飛行素材拖尾「飛行反方向」), state 卻只給位置與 facing, 沒有飛行方向(LoopRaider deepen-1 game-a 建置設計判斷, 非老闆回饋, 預防性) → 介面作者寫外觀時心裡有方向, 列欄位時只列了既有的 facing; 擊飛方向由「遠離炸彈工」決定, 和怪物面向無關, 照字面拿 facing 會在怪背對炸彈工時把速度線畫反 → 開工對介面時, 掃每個「依方向畫」的描述, 確認 state 裡有能推出方向的欄位: 有固定終點的(飛向資訊列某圖示)用終點座標自己算方向; 推不出的, 在 style.md 判讀約定寫明採用的約定(該作: flung 時飛行方向 = −facing, RD 要畫對就在擊飛期間把 facing 設成飛行反向), 回報請製作人補欄位(例 `vx` 或 `flyDir`), 列為出介面必查項(待製作人確認)〔P2〕

## 提案(來自 LoopRaider deepen-1 game-c 美術, 2026-11-18)

### 提案 1 — 合併到上方 game-a「提案 2」(方向性特效沒有方向欄位)當再現
- 同一份介面平行的 game-c 也撞到同一處, 而且初稿選了**相反**的約定(flung 時 facing = 飛行方向), 看到收件匣裡 game-a 的提案後改成「飛行方向 = −facing」: 怪物被擊飛時多半正面朝炸彈工, 這個約定讓 RD 不改 facing 就畫對, 錯的機率小(LoopRaider deepen-1 game-c 建置設計判斷, 非老闆回饋, 不算升格證據) → 證明這個約定不能留給節點各自決定: 兩款獨立開工會選出相反的方向, 而 RD 照哪一款都可能和自己那款美術對不上 → 補一句解法: 介面沒給方向、只能從現有欄位推時, 選「RD 什麼都不用改就最常對」的那個約定(以規則裡最常見的情況為準), style.md 寫明; 回報請製作人把方向欄位列為出介面必查項(待製作人確認)

### 提案 2 — 放進「與規格的分界」, 新經驗(同根因可併入上一條的通則)
- 介面 notes 要求「不足的那種看得出」(凱旋門卡片的三種花費), state 卻只給一個布林 `canAfford`, 也沒給持有數, 美術無從知道是哪一種不足(LoopRaider deepen-1 game-c 建置設計判斷, 非老闆回饋, 預防性) → 介面作者寫外觀時想的是逐項比較, 列欄位時沿用了關卡卡片那種單一布林 → 開工對介面時, 每條 notes 的「要看得出 X」都反查一次: 畫出 X 需要的資訊在不在 state 裡; 不在的話函式同時接受舊格式(布林, 退化成全部標紅)與補齊的格式(`{wood, ench, time}` 各自布林), style.md 判讀約定寫明兩種格式與建議傳哪一種, 回報請 RD 傳物件、請製作人改介面(待製作人確認)〔P2〕
